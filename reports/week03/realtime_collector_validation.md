# Week 03 실시간 데이터 수집기 검증 보고서

## 1. 실시간 데이터 수집 주기 및 적재 결과 검증

따릉이 실시간 대여소 현황은 Spring Scheduler를 이용하여 **5분 주기**로 수집하도록 구성하였다. `application.properties`의 cron 설정과 `@Scheduled` 설정을 확인하고, AWS EC2에서 실행 중인 서비스 로그를 통해 실제 수집 작업이 5분 간격으로 지속적으로 실행되는지 검증하였다.

EC2 서버 로그에서 수집 작업이 매 5분 간격으로 실행되는 것을 확인하였으며, `station_snapshot` 테이블의 일별 고유 `collected_at`을 집계한 결과 정상 운영일에는 하루 **288회의 수집 시점**이 적재되는 것을 확인하였다.

5분 주기로 24시간 수집할 경우 기대되는 288회와 실제 적재 결과가 일치하여 스케줄러의 정기 실행과 DB 적재가 정상적으로 이루어지고 있음을 확인하였다.

## 2. 수집 실패 및 장기 결측 구간 분석

누적된 `station_snapshot` 데이터를 기준으로 수집 시점 간 간격과 일별 수집 횟수를 확인하여 데이터 누락 구간을 분석하였다.

분석 과정에서 **2026년 8월 30일 17:15 KST 이후부터 2026년 8월 31일 20:40 KST까지 약 27시간 25분의 장기 수집 공백**이 확인되었다.

해당 시점의 EC2 서버 로그를 확인한 결과, 평소 수 초 이내에 완료되던 서울시 따릉이 API 요청의 응답이 비정상적으로 지연된 것을 확인하였다.

당시 수집기에는 외부 API의 장시간 응답 지연 및 비정상 응답 발생 이후 수집 작업을 정상 상태로 복구하기 위한 처리가 충분히 구현되어 있지 않았다. 이에 API 호출 timeout과 예외 처리 및 수집 작업 복구 처리를 보완하였으며, 서비스 재배포 후 **2026년 8월 31일 20:40 KST부터 스냅샷 적재가 다시 정상적으로 이루어지는 것**을 확인하였다.

### 2.2 API 재시도 로직 추가

단발성 외부 API 응답 실패로 인한 스냅샷 누락을 줄이기 위해 **페이지별 API 호출에 최대 3회의 시도 로직**을 추가하였다.

API 호출 또는 응답 데이터 검증에 실패할 경우 **2초 후 동일 페이지를 다시 요청**하고, 동일 페이지 요청이 3회 모두 실패한 경우에만 해당 수집 회차를 실패 처리하도록 보완하였다.

## 3. 14일 누적 완전 수집률 검증

실시간 수집기의 장기 운영 결과를 확인하기 위해 최초 수집 시점을 기준으로 **2026년 8월 25일 01:40 KST부터 2026년 9월 8일 01:40 KST까지 14일간**의 수집 결과를 분석하였다.

`station_snapshot` 테이블의 고유 `collected_at`을 기준으로 하나 이상의 대여소 데이터가 DB에 적재된 수집 시점은 **3,696회**였으며, 이 중 정상 대여소 수보다 적은 데이터만 저장된 불완전 적재 시점 5회를 제외하면 완전 수집에 성공한 시점은 **3,691회**이다.

따라서 14일간의 완전 수집률은 **91.54%**로 확인되었다.

완전 수집에 실패한 총 341회를 분석한 결과, 데이터가 전혀 적재되지 않은 수집 시점은 336회였으며, 이 중 장기 수집 공백 구간에서 328회, 단발성 수집 실패로 8회가 누락되었다. 이와 별도로 일부 대여소 데이터만 저장된 불완전 적재가 5회 확인되었다.

## 4. Stale 의심 데이터 검증

정기적으로 수집된 데이터가 동일한 상태로 반복 저장되는지 확인하기 위해 연속 수집 시점의 `bikes_available` 값을 비교하였다.

Stale 여부는 직전 데이터와의 비교가 필요하므로 정상적인 5분 간격인 **295~305초 범위**로 연속 수집되고, 해당 시점의 대상 대여소 데이터가 정상적으로 적재된 경우만 분석 대상으로 설정하였다.

초기 수집 구간에는 176개, 이후 구간에는 177개의 대상 대여소가 관측되었으므로 각 구간의 정상 대여소 수를 기준으로 비교하였다.

14일 동안 실제 적재된 3,696회의 수집 시점 중 stale 분석에 사용할 수 있는 수집 시점을 구분한 결과는 다음과 같다.

| 구분                  |        횟수 | 의미                                             |
| --------------------- | ----------: | ------------------------------------------------ |
| 직전 비교 데이터 없음 |         1회 | 분석 구간의 최초 수집으로 직전 데이터가 없음     |
| 불완전 적재           |         5회 | 정상 176/177개가 아닌 69/148/149개 대여소만 적재 |
| 비정상 수집 간격      |        13회 | 직전 수집과의 간격이 295~305초 범위를 벗어남     |
| 정상 비교 가능        |     3,677회 | 정상 대여소 수 및 정상 수집 간격 충족            |
| **합계**              | **3,696회** | DB에 존재하는 전체 수집 시점                     |

따라서 **3,677회의 수집 시점**을 stale 분석 대상으로 사용하였다.

이 중 모든 대상 대여소의 `bikes_available` 값이 직전 수집과 동일한 경우는 **2회**로 확인되었으며, stale 의심 비율은 **0.054%**로 나타났다.

단, 모든 대여소의 자전거 수가 동일하다는 사실만으로 서울시 API가 실제로 갱신되지 않은 데이터를 반환하였다고 단정할 수 없으므로, 해당 수치는 **API stale 발생률이 아닌 수집 데이터의 정체 여부를 확인하기 위한 보조 지표**로 활용하였다.

## 5. Capacity 데이터 완전성 검증

수요예측 모델의 정적 feature로 `capacity`를 사용하기 전에 대상 대여소의 capacity 데이터 완전성을 확인하였다.

Capacity는 서울시 따릉이 실시간 `bikeList` API에서 제공되는 `rackTotCnt` 값을 대여소 ID(`station_id`)를 기준으로 대여소 기본정보와 매핑하여 저장하도록 구현하였다.

로컬 환경에서 대여소 기본정보를 갱신한 후 `station` 테이블의 capacity 값을 확인한 결과는 다음과 같다.

| 항목                     |   결과 |
| ------------------------ | -----: |
| 대상 대여소 수           |  221개 |
| capacity non-null 대여소 |  177개 |
| capacity null 대여소     |   44개 |
| capacity 확보율          | 80.09% |

전체 대상 대여소 221개 중 177개에서 capacity 값이 확인되었으며, 44개 대여소에서는 capacity가 NULL로 확인되었다.

현재 capacity는 실시간 `bikeList` API 응답에 포함된 대여소의 `rackTotCnt`를 이용하여 매핑한다. 따라서 capacity가 NULL인 44개 대여소는 대여소 기본정보에는 존재하지만, capacity 수집 시점의 실시간 `bikeList` API 응답에서는 해당 `station_id`가 관측되지 않아 값을 매핑할 수 없었던 대여소이다.

이는 해당 대여소가 폐쇄되었거나 운영이 중단되었다는 것을 의미하지 않으며, 현재 실시간 API 응답만으로는 미관측 원인을 특정할 수 없다.

따라서 모델에서 `capacity` feature를 사용할 때는 NULL 값을 그대로 정상 capacity로 간주하지 않고, 실제 학습 대상 대여소와의 일치 여부를 확인한 후 결측 처리 또는 학습 대상 제외 여부를 결정할 필요가 있다.

> **검증 환경:** 로컬 MySQL DB
> **검증 결과:** 221개 중 177개 non-null, 44개 null
